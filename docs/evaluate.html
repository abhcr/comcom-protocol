1. Run the booking exchange

Use Node.js 24. This first evaluation requires no Python, API key, or account:

git clone https://github.com/abhcr/comcom-protocol.git
cd comcom-protocol
npm ci
npm run demo:v0.2

The runner starts the existing responder on an available local port, discovers its manifest, constructs a fresh booking, validates the result, and stops the responder automatically. It uses HTTP loopback and mocked authentication. The advertised example HTTPS URLs are mapped to that local server; this is development transport.

PASS discovery and pinned-profile manifest validation
PASS booking.create: HTTP 200, correlated and identity-bound result
PASS exact replay: identical response bytes
PASS changed request with reused key: HTTP 409 idempotency-conflict
PASS asynchronous booking: HTTP 202 → polling → completed
Evaluation passed. No external business service was called.

Each line is backed by an assertion. The command exits unsuccessfully on a mismatch. Inspect the runner to see the actual exchange and the booking contract for schemas and lifecycle rules. Authentication headers in this demo are not an authentication implementation.

2. Inspect Purplecore discovery

Deployment pending: the public routes returned website HTML during the 2026-10-04 evaluation. The local examples validate, but the command below must pass against the deployed site before launch.

The public endpoints are the RFC 9727 catalog and the company manifest. Run the following from the repository checkout. It performs two bounded HTTPS GET requests and validates their raw bytes against pinned local artifacts. Network or deployment failures fail the evaluation; do not replace missing evidence with a success claim.

node --input-type=module <<'NODE'
import assert from 'node:assert/strict';
import { createProtocolV02 } from './reference/v0.2/protocol.mjs';
import { secureFetch } from './reference/v0.2/secure-fetch.mjs';
const protocol = await createProtocolV02();
const catalog = await secureFetch('https://purplecore.in/.well-known/api-catalog');
assert.equal(catalog.status, 200);
assert.equal(catalog.headers['content-type'].split(';')[0], 'application/linkset+json');
const discovery = protocol.validateDiscovery(catalog.body, {
  method: 'GET', contentType: catalog.headers['content-type']
});
assert.equal(discovery.valid, true, JSON.stringify(discovery));
const profile = 'https://abhcr.github.io/comcom-protocol/releases/v0.2.1/profiles/manifest';
const link = discovery.value.linkset.flatMap(entry => entry.item)
  .find(item => item.profile === profile);
assert.ok(link, 'Expected the v0.2.1 manifest profile');
const document = await secureFetch(link.href);
assert.equal(document.status, 200);
assert.equal(document.headers['content-type'].split(';')[0], 'application/vnd.comcom.manifest+json');
const manifest = protocol.validateManifest(document.body, { manifestProfile: link.profile });
assert.equal(manifest.valid, true, JSON.stringify(manifest));
assert.equal(manifest.value.entity.id, 'https://purplecore.in');
assert.deepEqual(manifest.value.roles, ['discoveryPublisher']);
assert.deepEqual(manifest.value.capabilities, []);
assert.equal(manifest.value.contactUrl, 'https://purplecore.in/#contact-form');
console.log('PASS Purplecore discovery-only manifest', manifest.value);
NODE

The result identifies Purplecore Software Systems Pvt Ltd and points to its existing contact form. Empty profiles and capabilities mean it advertises zero interactions. The contactUrl is a navigation link, not a submission endpoint. This walkthrough never fetches that contact link or sends an enquiry.

To inspect the same shape without network access, select “Manifest” and “v0.2.1” in the browser checker, then “Load example”. That validates document shape only. The public command above additionally checks the live HTTP responses.

3. Decide what your project actually needs

Compare one business interaction with its exact capability contract. Check input/output semantics, lifecycle, retry/replay, reversal, permissions, and what your system can guarantee. A passing example is not enough to claim your service conforms.

  1. Pin an immutable release and verify artifact digests. The provided validators verify their local schema and registry bytes before use.
  2. Use the advertised manifest profile explicitly. v0.2.1 accepts the original interactive manifest or a discovery-only publisher; old validators do not understand the new profile. CLI/library defaults remain v0.2.0.
  3. Map one existing operation to a compatible draft capability. Bind identities using your authenticated transport; full response validation needs the original request and trusted transport.senderId.
  4. Exercise valid inputs, invalid inputs, duplicate requests, conflicts, lifecycle boundaries, and failure recovery before exposing the capability. Publish only interactions you implement.

No SDK or MCP server is required by this repository. Your current HTTP client can send the document; the CLI framing is the integration starting point. Python 3.13 plus requirements.txt enables the independent cross-validator checks via npm run conformance:v0.2.

Developer article draft

Can a business contract be small enough for an agent to evaluate?

Comcom is an experimental attempt to make business interactions explicit: discover a website's manifest, select an exact capability version, validate a typed request, and use the correlated result as the business record. The first reproducible exercise is booking creation.

Clone the repository and run npm ci && npm run demo:v0.2 with Node.js 24. The demo checks discovery, a booking result, exact replay, a changed request reusing the same key, and asynchronous completion. It uses loopback HTTP and mocked authentication; production identity and authorization remain the implementer's responsibility.

The second exercise is smaller. Purplecore's website publishes its company identity and a contact-page link through a discovery-only manifest. It declares no callable capabilities. That makes its existing enquiry route discoverable without implying that a business API exists.

Comcom is complementary to service descriptions and agent interfaces: it experiments with shared business capability semantics. All 201 catalog profiles are still draft. Purplecore and the booking responder are first-party examples; independent interoperability has not been established by those examples.

We are looking for narrow evaluations: does one booking contract fit your project, which fields or lifecycle rules do not, and can you reproduce the result? Use the walkthrough and submit an implementation report or a focused regression/documentation PR.
